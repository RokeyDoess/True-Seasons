# True Seasons — first v1 development build

Paper **26.3**, Java **25**, plugin version **0.1.4**. This is a working migration/snow milestone, not the finished v1 visual feature set.

## Implemented

- Four calendar seasons with a configured time zone and custom contiguous month ranges, including southern hemisphere calendars. Winter's version uses its starting year.
- Full-world discovery through read-only region headers and saved chunk generation status, inspected off the server thread; actual loads and edits use Paper. New chunks are never requested with generation enabled.
- Shared migration/cleanup engine, bounded async loads, per-tick application limits, TPS pause, a configurable player radius (default four chunks, a 9x9 area), nearest-first rings, reserved background time, and periodic rediscovery. Spring removal and uninstall cleanup prioritize this whole neighborhood.
- Compact, versioned per-chunk snow ownership (maximum 545 bytes) and seasonal versions in chunk persistent data. No global list of snow coordinates.
- Snow on all sky-exposed surfaces that support a vanilla layer, including wooden roofs, glass, leaves and upper slabs. Spring removal, block-edit ownership relinquishment, and fail-safe handling of changed blocks or ambiguous snow layers remain intact.
- Gradual, scattered winter accumulation near player neighborhoods, capped at the persistent shared winter coverage; remote chunks fill in one pass. Local stages advance together when only nearby work remains. Partial column cursors resume after restart; progress reports a chunk complete only after all columns have been considered.
- Durable manual overrides, pause state, tracked worlds, cleanup intent, and BlueMap request queue.
- Optional BlueMap adapter with durable final-chunk revisions, saved-file verification, separate completion receipts for every map, and bounded region batches. Interrupted transitions and newer changes remain queued until their final state is rendered and saved.
- Native Minecraft snowfall for every winter rain/thunderstorm, using client-only cold biome aliases. Saved biomes remain unchanged and clear weather stays clear. No particle simulation or client mod.
- New terrain generated by player exploration joins winter migration, including previously indexed unfinished terrain. Matching version stamps cannot hide a pending transition.
- Rain replenishes broken winter snow in loaded, completed chunks throughout winter, without restarting migration. Random sampling and a broken-snow queue use vanilla support/light checks and leave vegetation and existing layers intact.
- Colored administration output begins with **Migration status**, highlights progress and coverage, and explains why map requests are waiting.
- Restart reads saved completion directly from chunk PDC; unchanged configuration reloads preserve migration versions and progress. TPS aggregation is cached for one second across migration, snowfall and command requests.
- An introductory winter snowstorm lasting through terrain migration, configurable natural rain/thunder rules, administration commands, permissions, public service API, and lifecycle events for future adapters.

## Still required for the complete v1

**Configured grass/foliage palettes are not rendered yet.** `visuals.yml` and the central resolver expose biome-family palettes through the API. The native snowfall adapter preserves explicit biome effects, but lowering client temperature can affect vanilla climate-derived grass/foliage tints. BlueMap reflects physical seasonal snow; a matching seasonal color adapter remains a future milestone.

Distant Horizons integration is intentionally absent. Its future adapter can use the public API and events without adding a dependency to the migration engine. Essentials, Vault, Chunky, BMMarker and LuckPerms do not require integration; they are simply part of the test environment.

## Build and install

The local build uses the already installed test server's libraries and BlueMap jar, without downloading another server or changing its configuration:

```powershell
cd 'E:\True Seasons\TrueSeasons'
.\build.ps1
.\build.ps1 -Install
```

Pass `-JdkDirectory` or `-ServerDirectory` if their locations change. The output is `build/libs/TrueSeasons-0.1.4.jar`. `-Install` copies this jar into the test server's `plugins` folder and retains older TrueSeasons jars with a `.disabled` extension. Normal startup adds missing commented configuration options and removes obsolete particle and storm timer settings.

A conventional Gradle project is also included, pinned to the test server's Paper API build and a published BlueMap API. With Gradle installed, run `gradle clean check jar`. There is no Gradle installation or wrapper bundled in this first workspace setup; `build.ps1` is the verified local build path.

The precipitation adapter targets Mojang-mapped Paper **26.3 build 177**. The render-completion bridge targets **BlueMap 5.29**: its public API exposes scheduling acceptance rather than completion, so the isolated bridge tracks native update tasks through their final map-save work. A compatibility failure retains requests and appears in `/ts status`; it never reports a false map completion.

## Try it

Start your test server normally, then use:

```text
/ts info
/ts status
/ts season set winter
/ts migration pause
/ts migration resume
/ts season set spring
/ts season sync
```

`season set` persists a manual override until `season sync`. `reload` validates all six configuration files before applying them. Unchanged settings preserve progress; changes to snow-placement rules or world eligibility start a new revision. The default calendar follows March–May spring, June–August summer, September–November autumn, and December–February winter in America/Los_Angeles.

Only overworld dimensions are enabled. The `worlds` list can restrict these by Bukkit world name. Previously managed worlds remain in the cleanup manifest even if subsequently excluded. An unavailable tracked world prevents removal-safe status; load that world so it can be restored.

## Clean removal

```text
/ts cleanup
/ts cleanup confirm
/ts status
```

Confirm within 60 seconds using the same sender. Cleanup stops seasonal edits, traverses all tracked worlds without generating chunks, restores owned snow, and removes chunk metadata only after successful restoration. Unexpected non-snow replacements are preserved. Unexpected snow-layer counts retain ownership and defer the chunk instead of reporting a false success.

Wait for **Plugin removal safe: YES**, then **stop the server normally** so its final saves finish. Remove the jar after shutdown. Cleanup also verifies removal of temporary BlueMap chunk markers. For the restored map to finish before removal, additionally wait for **pending regions: 0**. Disabled/frozen renderers can retain map work independently of successful world restoration.

After cleanup completes, True Seasons stays in restored mode. `season sync` or `season set` explicitly enables seasonal behavior again. A startup after cleanup revalidates the saved chunks before reporting removal-safe status again.

## Persistence and performance notes

Job intent and shared winter coverage live in `plugins/TrueSeasons/state/jobs.yml`; BlueMap's chunk revisions, per-map receipts and marker-purge queue live in `state/bluemap.journal` and `state/bluemap.snapshot`; older `state/bluemap.yml` queues import automatically. Small forced journal appends precede edits, while snapshot compaction runs off the server thread. Chunk versions and snow ownership live in that chunk's PDC and are saved with its blocks by Paper. On restart the index is rebuilt and saved PDC is checked: already migrated chunks skip edits, while incomplete chunks are retried. Unfinished terrain entries are excluded from the completed/total counters and become eligible when Minecraft finishes generation or periodic discovery finds them complete. Unchanged rediscovery leaves completed work intact. Newly generated terrain can add real work to the denominator; BlueMap's separate queue never restarts terrain migration. Saved matching PDC hydrates completed counters directly during startup indexing, without replaying the full chunk traversal. Changed or partial saved metadata reopens only its required work. Unchanged reloads preserve the current revision; changed snow-placement rules or world eligibility require a new migration.

No persistent plugin chunk tickets are used. They can propagate ticket levels into neighboring chunks and induce generation. Work runs inside Paper's non-generating load completion callback; excess work is requeued rather than holding a chunk across ticks with a ticket. The time budget is a soft boundary between chunks; it cannot interrupt Paper's own chunk load or a single chunk's application halfway through.

BlueMap requests wait until a read-only region/NBT check finds a unique final revision token saved with the edited chunk. Each configured map must then finish its native render and map-save task for that revision. A later edit invalidates older receipts. Temporary proof markers are removed through bounded, non-generating loads; cleanup verifies that removal on disk. Keep Paper's normal autosave enabled. Map updates can trail in-game changes, especially for chunks that stay loaded. True Seasons does not start or stop BlueMap's renderer or force a whole-map render. Confirmed removed source regions receive bounded forced region updates so old map tiles can be cleared; requests retire only after final save receipts. Missing or corrupt world directories remain pending with a visible reason.

Snow defaults to `surface-mode: all-exposed`; the optional material whitelist is used only with `surface-mode: whitelist`. Placement checks the highest non-air block in each column, then vanilla snow support. This covers roofs and leaves without putting snow under them. Occupied plants, existing snow and fluids are preserved; unsupported shapes such as fences and lower slabs cannot hold a vanilla layer. The old shipped biome exclusions are migrated to an empty list; customized exclusions remain intact. Regular player edits and vanilla snow formation are handled through events. External editors that replace owned snow with identical block data without firing Bukkit events must call `TrueSeasonsApi.relinquishSnowOwnership` first; an identical unannounced replacement cannot be distinguished from the original block by any block-data comparison.

`snow.yml` controls `transition.columns-per-step` (16) and `transition.step-ticks` (5). Winter chunks near players cycle through scattered surface columns, with earlier placements retained during subsequent steps. Shared transition coverage measures the fraction of eligible surface columns already considered across enabled worlds, including partial chunks; it is not a literal percentage of blocks holding snow. Its saved high-water mark never drops as exploration adds terrain. Each local placement step stops at the shared coverage cap. When only local chunks remain, the next shared stage advances after every local chunk catches up, preventing a circular wait. Leaving a neighborhood lets background processing finish the remaining columns in one pass. Spring and cleanup remove owned snow in one pass per chunk rather than staging its removal. `config.yml` controls `migration.player-radius-chunks` (4).

`weather.yml` enables the introductory winter storm and native precipitation through `snowfall.enabled`. The storm lasts until that world's terrain migration completes, including pauses, and resumes after a normal restart. It does not wait for BlueMap rendering. Every biome sent to a client has a private cold alias available from login. Throughout winter, outgoing chunk and biome packets refer to those aliases; leaving winter, entering an excluded world or starting cleanup refreshes already-sent chunks with their original biome IDs. Physical accumulation remains the separate tracked snow system, covering exposed vanilla-supported surfaces even in warm server biomes. The introductory storm's prior rain, thunder and clear-weather timers are journaled and restored on completion, season change, cleanup and shutdown. Normal restart/login initializes the aliases; players already connected during a hot plugin load must reconnect once. Disconnected players no longer produce a misleading reconnect warning. Future Paper versions require adapter verification.

After terrain migration completes, winter rain replenishes missing layers in already loaded chunks. Warm saved biomes cannot form native server snow merely from client climate aliases, so the helper makes bounded vanilla-style placement attempts: at most eight chunks and 64 sampled columns per tick, with a 1 ms soft planning budget. It prioritizes broken snow, honors block light below 10, sky exposure, support, configured exclusions and the snow accumulation gamerule, and emits block-form events. Durable map intent and ownership precede block writes; forced disk commits can exceed the planning budget. It never loads or generates a chunk, replaces ground cover, grows existing layers or restarts migration.

## Integration API

Obtain `dev.trueseasons.api.TrueSeasonsApi` through Bukkit's `ServicesManager`; call it on the server thread. It exposes the season, progress, shared visual profile, a chunk's seasonal version, cleanup state and ownership relinquishment. `SeasonChangeEvent`, `SeasonChunkUpdatedEvent` and `SeasonMigrationEvent` provide world/season changes, chunk completion and migration/cleanup start/completion. The chunk event reports whether physical blocks changed. No DH classes appear in the core.

## Verification

`build.ps1` compiles the jar and runs calendar, migration, metadata, BlueMap receipt and actual Minecraft packet/biome decoder tests. `verify-server.ps1` creates a disposable clone under `run/verification`, starts four stop/start cycles with the real plugin stack, and checks placement, partial recovery, explicitly explored new terrain, stale pending markers, spring restoration, conflicts, cleanup, non-generating migration and BlueMap render completion. It never starts or modifies the original test server's world. The clone binds Minecraft to localhost on port 25585 and disables its BlueMap webserver.

The probe jar is a test-only fixture editor and must never be installed on your normal server. The verifier intentionally refuses to overwrite an existing verification folder. Rename an old run within `run` before starting a fresh one. Per-cycle logs and the result file stay in the verification folder for inspection.

After the main verifier passes, `verify-final-map.ps1` exercises the final tile/save barrier against actual map storage. Then `verify-optional.ps1` runs the saved-world revalidation with BlueMap absent in that same clone. See [validation details](docs/VALIDATION.md) for the completed checks and their limits.
